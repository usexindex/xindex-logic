01 / The thesis

Less wallet
management. More product.

Tokenized markets make individual exposures more portable. They do not automatically make a multi-asset strategy easier to use. If a user wants seven exposures, they still inherit seven balances, seven decisions, and seven possible liquidity paths.

The wallet clutter problem

A portfolio can be diversified in theory and still feel fragmented in practice. Separate tickers create operational friction at every step: acquiring exposure, monitoring it, moving it, pairing it, and exiting it.

01Many referencesSeveral tokenized stocks represent the exposure a user wants.
→
02Many balancesEach ticker becomes another position to manage and explain.
→
03One answerA basket token composes the set into a single product.
The Xindex answer

One liquid basket token.

Deposit USDG and receive a token that represents a defined basket. Hold it as one position, trade it as one asset, or use it as one side of a liquidity pair.

Example

$AI7 = NVDA + AVGO + TSM + AMD

The product thesis

The value is not only in the underlying references. It is in the packaging: a fixed, legible composition that can move through a wallet, a vault, or a liquidity pool without asking the user to recreate the same allocation every time.

02 / The basket model

Compose once.
Use everywhere.

A basket is a product with a defined composition, a mint/redeem path, and a market role. It is not a promise that every underlying asset behaves the same way, nor a replacement for understanding the references inside it.

01Reference catalogueStart with canonical Robinhood Stock Token references and a published composition.
→
02Basket definitionExpress the intended exposure as one named product with transparent weights.
→
03Vault interfaceLet users simulate or execute a deposit, mint, redeem, and fee path.
→
04Liquidity roleUse the basket as an asset that other projects can pair against.

What a basket standardizes

LayerWhat is defined
IdentityName, symbol, and product purpose
CompositionUnderlying references and target weights
ConversionDeposit and redemption relationship
Market roleAn asset that can be held, traded, or paired
DisclosureEstimates, execution limits, and risks shown plainly

Design rule

Make the wrapper legible.

A user should understand what a basket contains before deciding whether to hold it. A project should understand what it is pairing against before bootstrapping liquidity.

Important distinction

Reference prices and weights describe the product. They are not a guarantee of execution price, liquidity, or future performance.

Mint flow

  1. Choose a basket. Select one of the initial products and review its composition.
  2. Enter a USDG amount. The interface shows the fee and an estimated basket output.
  3. Review before action. The user sees the reference value, target weights, and simulation disclosure.
  4. Receive the basket. In a live implementation, the vault would execute against the approved contract path.

Redeem flow

Select a basket amount, review the estimated USDG output and fee, then confirm the redemption path.

Same principle: show the conversion before the user commits.

Estimate is not execution

Reference values, displayed fees, and calculated outputs are illustrative until a live transaction is configured and executed. Market movement, liquidity, contract state, network conditions, and implementation details can change the final result.

06 / Product before token

The token is
the fee engine.

Xindex does not lead with a token launch. It leads with products people can understand and use. If basket demand, vault activity, and liquidity pairs develop, a future project token can be introduced around the economic activity those products create.

01 / Product layer

Baskets are the product.

Build assets people genuinely want to hold, trade, and pair.

02 / Revenue rail

Fees follow usage.

Mint, redeem, and future basket listing activity can support a transparent fee model.

03 / Future token

Utility comes later.

A token can be tied to protocol fees and governance after the product foundation exists.

The sequencing principle

Do not launch the token first.

A token should not have to manufacture the reason the protocol exists. The baskets establish that reason. Adoption, useful liquidity, and vault volume provide the context for later utility.

07 / Canonical references

Trust starts
with the reference.

A basket product is only as understandable as the references beneath it. Xindex is designed around canonical Robinhood Stock Token references, explicit weights, and a clear distinction between a reference catalogue and executable liquidity.

Reference discipline

PrincipleMeaning for users
Canonical referencesBasket components should point to the intended official catalogue entries, not lookalike proxies.
Visible compositionWeights and underlying names should be inspectable before a user chooses a basket.
Reference price clarityDisplayed values are reference estimates; they do not guarantee execution.
Separate liquidity proofA listed reference and an executable market are related but distinct questions.
Non-custodial intentThe vault should not imply that Xindex takes custody of user assets.

What this does not mean

A tokenized stock reference is not the same as owning the underlying company share. It may provide economic exposure under the terms of its own instrument, without share ownership or voting rights. Users must review the applicable terms and restrictions.

08 / Roadmap & risks

Build in public.
Ship in stages.

The sequence matters. Xindex should move from a clear product concept to verified implementation without letting the language of a prototype outrun the reality of the system.

Phase 01 / Product clarity

Define the initial catalogue

Finalize the basket names, intended compositions, reference entries, user flows, and disclosure language for $AI7, $MAG7, and $GOLD.

Phase 02 / Contract readiness

Verify the conversion path

Implement and review the non-custodial vault path, pricing/reference boundaries, mint/redeem behavior, and fee accounting.

Phase 03 / Market utility

Prove the pairing use case

Establish basket liquidity and demonstrate why new projects can use a basket as a practical counterpart.

Phase 04 / Future utility

Evaluate token economics

Only after product usage exists: assess a future fee-engine and governance token with a clear purpose.

08B / Risk register

Know the limits.
Design around them.

A useful basket interface makes risk easier to inspect; it does not make risk disappear. The protocol path and public language should remain explicit about what can change.

Risks to understand

  • Underlying exposure riskBasket diversification does not remove price movement or concentration risk inside a composition.
  • Liquidity and execution riskReference values may not equal the price available in a live market or redemption path.
  • Contract and oracle riskSoftware, reference data, and external dependencies can fail or behave unexpectedly.
  • Instrument and jurisdiction riskTokenized references may have eligibility, transfer, geographic, or legal restrictions.

Prototype boundary

The current Xindex experience is frontend-only and includes simulated interactions. It is not a connected wallet, a live order router, or a completed on-chain protocol.
